# 代码实现

## 使用约定

本 Skill 独立安装和升级，方法、模板和参考 Schema 均在本目录。按当前任务读取必要资料；使用 PATH 中独立安装的 `swe-cli`，命令和覆盖边界见[CLI 约定](references/cli.md)。`contract.json` 只声明适用产物类型，不要求全部输入齐备，也不授权额外写入。

## 责任与范围

只修改明确指定模块的生产代码、生产依赖和必要实现配置。程序内部的对象创建、连接、启动关闭属于本领域；发布流水线、环境部署配置属于部署领域。业务模型、架构 YAML、独立协议、测试代码、断言、快照、测试数据及测试配置只读。

模块目录含测试时必须细化为生产文件清单，不以整个模块目录获得测试写入权。源码中的接口声明若是独立权威契约，也须作为只读依据，不能通过修改公开承诺消除实现错误。需要测试补充、设计变更或部署接入时交代原因与受影响对象，本次只报告职责外缺口，不扩大生产代码范围。

## 专业方法

实现前读取相关业务与模块契约，以及[实现运行约束](references/standards/implementation.md)。按当前模块需要使用[模块质量方法](references/implementation.md)，审查代码时读取[审查方法](references/review.md)，核对组织与依赖时读取[结构审查方法](references/structure-review.md)。

沿真实入口、消费者、数据、状态与资源生命周期判断变化，保留既有行为。高风险重构依赖必要行为证据，缺口记录为必要测试证据未具备；不在此编写单元测试。依赖、类型、错误和外部能力接入保持在所属模块，不让框架回调和技术细节扩散业务规则。

## 检查与修正

修改前明确对应模块路径和允许依赖。实现后执行相关构建、类型或静态检查、代码自审，并运行已有相关测试；运行前限定缓存、日志等产物位置，禁止更新测试快照或使用会重写断言的模式。

YAML 项目执行 `system-design check`。目录、文件归属和必要文件是语言无关检查；源码依赖只有匹配到语言适配器时才被验证，当前内置 Go、TypeScript 和 C++。其他语言或无法解析的构建结构必须列为未验证，并用项目已有检查补充。Markdown 项目使用 `structure` 与项目依赖检查；旧 `structure` 不解析源码依赖。发现测试失败，先区分生产缺陷、预期问题和环境问题，只修正授权生产代码，不放宽测试。

## 交付与只读模式

交付生产代码变更、实际验证与未覆盖项，说明职责外缺口与影响。只读审查遵守本 Skill 的只读边界，完成条件是有证据的发现与覆盖说明，不要求消除问题；禁止通过临时副本或缓存写入绕过只读边界。
