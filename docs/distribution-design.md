# 分发设计

## 目标与当前状态

本文负责 `reed` 服务、`swe` CLI、Skill 和插件的构建、打包、安装、更新与卸载。系统职责与阶段见[系统设计](system-design.md)，命令、结果协议与服务运行约束见[应用设计](app-design.md)。

当前源码提供独立 `reed` 管理服务、`swe` 检查 CLI、纯文本 Skill、六平台插件验证包、Codex 和 Claude 清单，以及 DSH 架构页签适配。插件不包含管理服务；未发布本次产物到市场，宿主实机安装仍需验收。

插件市场作为宿主内的正式安装、更新入口，独立二进制仍可单独使用。本文的包名、路径与安装命令对应当前源码构建，不表示旧 Release 已包含这些产物。

## 目标产物与依赖

| 产物 | 目标内容与依赖 |
| --- | --- |
| `reed` 服务 | 通用管理、调度与运行约束，管理目标、任务、Skill 和运行；按业务需要调用领域工具 |
| `swe` CLI | 独立 SWE 校验、设计渲染与迁移阶段的架构服务；不依赖 `reed`，不内嵌 SWE Skill |
| SWE Skill 文本包 | 专业方法和资源，使用可用且兼容的 `swe`；不要求 `reed` |
| SWE 宿主插件 | 组合 SWE Skills、`swe` 与宿主适配；使用者可以不安装管理服务 |
| 服务与工具组合发行 | 按实际场景组合 `reed`、领域工具和 Skill，显式记录各自版本与兼容要求 |

两套程序各自构建、测试和发行，产物与验证脚本归各自应用目录。组合发行可以使用同一版本值，但不能以同号代替运行时工具版本与结果协议兼容检查。`skills/` 保持唯一 Skill 源码来源，`reed` 按明确来源加载，插件从同一来源打包，不维护可编辑副本。

旧 `reed` 包是检查程序，本次同名包是管理服务，不是行为兼容升级。原检查调用迁至 `swe`；管理服务、工具与各自状态独立安装。

## 当前产物组成与来源

| 产物 | 内容与边界 |
| --- | --- |
| 独立二进制 | `reed` 管理服务与 `swe` 专业工具分别构建，不内嵌领域 Skill |
| 纯文本 Skill 包 | 每个 Skill 自包含知识、方法、模板与 Schema，不携带二进制，不依赖其他 Skill |
| 宿主插件 | 组合 Skill、独立工具目录中的二进制与宿主适配；二进制不放进 Skill 目录 |

仓库 `skills/` 下的六个目录是 Skill 的唯一源码来源；`reed` 来源加载与插件打包读取明确的 Skill 内容，不维护第二份源码。插件组合不改变 Skill 的独立资源边界。

## 安装与版本

CLI 独立发行 `swe_<os>_<arch>.tar.gz`，归档包含 `swe/bin/` 与版本摘要清单。校验发行摘要后将二进制目录加入 PATH，通过 `swe version` 确认版本；Windows 使用 `swe.exe`。Skill 是独立纯文本包，不携带二进制，也不绑定其他 Skill 的版本。项目记录所用 CLI 版本与来源；进行中的范围基线继续使用创建它的工具，不通过升级重建基线掩盖改动。

Skill 可从独立的 `<skill-name>.tar.gz` 文本包解压到临时目录，核对内容后将选定的 `skills/<skill-name>/` 放入宿主的 Skill 目录。插件管理的资源通过宿主更新，不覆盖宿主管理目录。CLI 缺失或版本不兼容时报告无法检查，按项目约定安装独立 CLI。

## 当前构建、版本与市场接入

从仓库根目录运行：

```bash
bash plugins/build.sh 0.1.0
```

版本为无 `v` 前缀的 SemVer。复用独立 CLI 六平台构建及六个纯文本 Skill 包，输出 `apps/swe/dist/reed-plugin_<系统>_<架构>.tar.gz`，展开目录在 `apps/swe/dist/plugins/<版本>/<平台>/`。包内 `runtime.json` 固定 CLI 版本与摘要。

Codex、Claude 清单由相同版本生成，均引用 `./skills/`，各平台验证包包含完整运行资源。两个市场的平台选择及实际安装仍需验证，不能将构建成功描述为市场可安装。

DSH npm 主包位于构建目录的 `dsh-reed/`，六个平台子包为 `dsh-reed-<系统>-<架构>/`。主包以固定版本的 `optionalDependencies` 选择平台，安装脚本校验子包 SHA-256 后将二进制放入独立工具目录并向宿主暴露命令；插件版本不与 CLI 版本绑定，`runtime.json` 自带 CLI 版本由服务启动时核对。禁用安装脚本时需显式运行包内 `node install.mjs`。发布顺序为六个子包、主包、市场登记；本地平台验证归档不是六次同名 npm 发布。

接口依据见 [Codex 插件打包](https://developers.openai.com/plugins/build/plugins)、[Claude 插件清单](https://code.claude.com/docs/en/plugins-reference)和 [DSH Skill 注册接口](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/skill/skill/src/index.ts)。

构建、打包与生成清单使用同一次发行的版本值；现有协议允许 Skill、插件与 CLI 独立演进，不意味着每次发行必须人为指定不同版本。运行时实际使用的 CLI 版本与摘要由 `runtime.json` 明确记录，服务复用按应用设计核对。

工具包与插件内部工具路径使用 `swe`、`tools/swe/`。插件产品名 `reed-plugin`、`dsh-reed` 及兼容架构路由 `/reed/` 保留，避免同时改变已有宿主身份；它们不代表管理服务。

`apps/reed/scripts/build-release.sh <版本>` 独立构建六平台 `reed_<os>_<arch>.tar.gz` 到 `apps/reed/dist/`，包含 `reed/bin/reed`（Windows 为 `.exe`）及使用说明，目录附 SHA256SUMS。配置和运行记录由用户存放到显式目录，不打包凭据、Agent 或项目状态。`reed version` 核对服务版本。

## 当前 DSH 宿主接入

插件通过 `skills.register` 分别注册六个 `swe-*` 入口，不注册总协调入口。每个 Skill 从自身目录加载必要文档和参考 Schema，彼此无依赖；宿主将独立 CLI 暴露为 `swe` 命令。

插件通过 `webServer` 注册并代理[应用设计定义的固定路由](app-design.md#路由与宿主协议)，前端使用 Go 返回的项目 URL 展示同源 iframe。插件配置 `root` 为项目共同工作区；未配置时使用 DSH 进程工作目录。

```yaml
- insert:
    - id: reed
      name: dsh-reed
      config:
        root: /absolute/workspace
```

插件首次收到请求时连接服务，未启动时调用包内 CLI。复用、启动和关闭遵循[服务所有权与生命周期](app-design.md#所有权与生命周期)。插件卸载只注销自己注册的 Skill、路由与自己启动的服务。

## 拆分迁移与服务生命周期

1. 将 SWE 检查、渲染、Schema 与测试迁至 `apps/swe/`，将 Skill 工具命令、独立工具包、运行绑定、插件工具路径与对应验证一起改为 `swe`。已有检查协议尽量保持稳定，必要变更须明确兼容策略。
2. 先保留 `swe system-design serve`，同步 DSH 启动与版本核对，维持现有独立架构图消费者。旧固定端口和路由的归属以应用设计为准，不让两套服务争用同一地址。
3. SWE Skills 保留独立文本包与插件分发；说明替代资源获取方式后移除现有内嵌绑定，不将其搬入 `swe`，不恢复安装器。
4. `reed` 服务就绪后按明确来源加载 Skill，并通过领域工具接入展示架构图。若改变宿主服务所有权，须同步启动、关闭、复用与升级行为，避免卸载一个消费者停止其他消费者仍在使用的服务。
5. 迁移旧安装时区分原检查二进制、未来管理服务、Skill 与运行记录；更新工具入口及 PATH 后核对实际版本，不凭包名相同认定兼容，不删除用户项目产物。

边界拆分验收必须在未启动 `reed` 的条件下验证 SWE Skills、`swe` 和插件；组合场景另外验证管理服务调用专业工具。构建成功不代表市场或目标平台可用。

## 更新、卸载与迁移

插件管理的资源通过宿主更新和卸载，独立安装不覆盖宿主管理目录。独立二进制按发行摘要校验后替换；移除独立安装时只清理其二进制与 PATH 配置，不清理业务项目的目标、任务或交付。

独立二进制和 Skill 文本包提供本地可验证的获取方式，插件调用链由集成测试验证。市场尚未验收时不能把市场安装作为唯一替代入口，也不能将本地验证包描述为市场可安装。旧安装器不再保留；迁移完成条件统一以系统设计为准。

当前范围基线不得借升级重建；目标调度运行记录的跨版本读取与迁移须遵循应用设计确定的格式兼容规则，格式未确定前不承诺无损接续升级。

## 待验证事项

1. Codex、Claude 市场的平台选择与实机安装、更新、卸载。
2. 拆分后的工具包、服务包、Skill 与插件在目标平台上的独立使用及组合接入，交叉构建不替代实机验收。
3. 目标运行记录格式确定后的升级兼容要求。
