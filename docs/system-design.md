# 系统设计

> ReedHarness 实现 Harness 的 Business 层：GitHub 管目标与任务，Agent 做判断与执行，Skill 提供完成能力，`reed` 服务负责管理、调度与运行约束，`swe` CLI 为 SWE Skills 提供独立的专业校验能力。

目标方案按职责拆分通用管理服务与领域工具。源码已按本方案拆分，管理、调度、任务验收、GitHub 回写与首个 Codex 接入已实现。验收区分本地控制逻辑、真实 Agent 接入与实际业务效果。

## 定位

Harness 由 Environment、Agent、Business 三层组成。ReedHarness 只自建 Business 层：

| 层 | 做法 |
| --- | --- |
| Business | 复用 GitHub 管理目标、任务与证据；自建 Loop 调度、约束与检查，提供领域 Skill |
| Agent | 选用 Codex、Claude Code、pi 等现成 Agent，不自建模型调用与 Agent 循环 |
| Environment | 不自建沙箱，只配置和核对工作区、权限、凭证与预算 |

建设目标：在明确的目标、授权与资源边界内，系统自主形成任务、执行、验证并根据结果继续或调整。人决定目标、重大取舍与授权，并对结果负责。SWE 是首个验证领域。

## 核心概念

| 概念 | 是什么 | 谁判断 |
| --- | --- | --- |
| 目标 | 预期变化、基线、效果证据、授权、预算、停止条件 | 人确定；Agent 在委托内评价进展 |
| 任务 | 本次要解决的问题、输入、交付物、验收条件、授权 | Agent 定义与执行；程序检查与独立审查验收 |
| Skill | 一类工作的知识、方法、工具与检查 | Agent 按任务选用 |
| Loop | 由事件或定时任务触发，根据当前状态决定如何推进目标 | 确定性响应由 `reed` 按规则处理；业务判断交给 Agent，`reed` 检查约束并落实调度 |

委托可以停在任意一层：只用 Skill 和检查命令做局部工作；交给 `reed` 调度 Agent 完成一个任务；或交给 Loop 推进整个目标。

## GitHub 与状态归属

一个业务仓库承载代码、文档、任务与交付，关联的 GitHub Project 管理目标。首版一个 Project 对应一个 Goal，一个仓库 Issue 对应一个 Task。Project 属于用户或组织，再关联到仓库；目标与任务记录不另存一份到 Git。

| 对象 | 权威位置 | 内容与修改责任 |
| --- | --- | --- |
| Goal | Project README | 目标、基线、效果标准、授权、预算与停止条件由人确认；进展与评价单独记录，由 `reed` 根据 Agent 结果回写 |
| Task | Issue | 问题、输入、交付物、验收条件与任务授权由 Agent 提出，`reed` 检查后创建或更新；结果与证据写入评论 |
| 任务进度 | Project 的任务状态字段 | `reed` 根据调度与验收结果更新；完成时同步 Issue 状态，取消不算成功完成 |
| 交付与证据 | PR、commit、检查结果及证据链接 | 关联到对应 Issue；目标评价记录引用实际效果证据 |
| 运行与恢复记录 | `reed` 本地运行目录 | 由 `reed` 保存运行标识、触发处理情况、Agent 会话、工作区、检查点和待回写结果，不另建 Goal/Task 数据库 |

GitHub 是业务状态的唯一事实来源，本地记录只支持调度与恢复。目标定义的变更须由人确认，进展回写不得修改已确认的目标、评价标准、授权与预算。

## 事件与定时驱动的 Loop

Loop 不是从规划到验收依次执行的固定流水线。执行、检查、审查和目标评价都是按当前状态与需要调度的工作。

每轮流程：

1. 接收事件或定时触发，定位相关 Project、Issue 与运行记录。
2. 读取当前状态，核对授权、预算与停止条件。
3. 确定性响应按规则处理；需要业务判断时调度 Agent，决定创建任务、执行、检查、审查、评价目标、等待、请人决定或结束。
4. `reed` 检查决策是否符合约束，落实调度并记录状态，本轮结束，不等待整条工作流程完成。
5. 后续工作结果、状态变化或下一次定时触发再次进入 Loop。

| 触发示例 | 可能的响应 |
| --- | --- |
| 目标启用 | 调度 Agent 分析目标、规划任务 |
| Issue 更新、任务就绪 | 核对当前状态，调度任务执行 |
| Agent 提交交付 | 调度适用检查或独立会话审查 |
| 检查或审查返回 | 推进验收、调度修正、记录受阻或请人决定 |
| 任务完成 | 判断是否推进其他任务或评价目标 |
| 定时触发 | 检查进展、发现停滞、采集目标效果 |
| 人工回复 | 核对决定并恢复等待中的工作 |

事件只是触发依据，不能代替当前状态。重复或同时到达的触发不得导致同一工作重复调度；中断后须能核对状态并接续，不能因结果同步失败而重复已完成的工作。具体调度与恢复机制见[应用设计](app-design.md)。

## 硬规则

以下规则由程序强制，不依赖提示词：

1. 任务授权必须是目标授权的子集。
2. Agent 不能修改目标、评价标准、授权与预算，只能提出变更，由人确认。
3. 任务完成不等于目标达成。目标评价使用目标定义的效果证据，并在评价时重新采集。
4. 调度前检查预算与停止条件；无法满足执行所需的权限约束时不得启动相关工作。权限隔离复用 Agent 与 Environment 提供的能力，范围检查不能代替权限隔离。

## 系统组成与设计入口

| 组成 | 职责与边界 |
| --- | --- |
| `reed` 服务 | Business Harness 管理与调度中心：管理目标、任务、Skill 和运行，接收事件与定时触发，调度 Agent，落实授权、预算与恢复规则 |
| `swe` CLI | SWE 领域工具：检查架构、文档、产物关系、实现映射和改动范围，生成架构图；不管理目标、不调度任务、不授予权限 |
| SWE Skills | 提供专业知识、方法、工具用法、验收依据与异常处理；不保存具体任务状态 |
| Agent | 根据目标和任务进行规划、执行、专业判断、审查与效果评价，按需调用领域工具 |

运行约束归 `reed`，专业校验归 `swe`。例如 `reed` 核对任务能否写入某个目录，Environment 落实权限隔离；`swe scope` 检查实际改动是否符合约定范围，不能代替权限隔离。`reed` 可以调度专业检查并记录结果，不内置另一份 SWE 规则，也不将检查退出码直接当作任务完成。

独立工作时，Agent 读取 SWE Skill 并调用 `swe`，无需启动 `reed`。目标推进时，由 `reed` 调度 Agent；Agent 仍通过 Skill 使用相同的 `swe` 工具。换一个业务领域时增加相应 Skill 和工具，不重写通用管理与调度核心。

`reed` 的管理页面提供目标、任务、Skill、运行及系统设计入口。目标与任务以 GitHub 为权威来源；Skill 管理先提供目录、来源、版本与能力可用性查看和选择，不维护第二份可编辑内容。系统设计是首个领域功能，页面调用 `swe` 获取诊断与架构展示，设计文件仍保存在业务项目中，生成页面和缓存不成为权威来源。

三份设计各自维护唯一的职责范围：本文负责 Harness 的业务协作、硬规则与实施阶段；[应用设计](app-design.md)负责 `reed`、`swe` 的模块、接入、交互和运行；[分发设计](distribution-design.md)负责服务、CLI、Skill 与插件的构建和交付。

## 当前实现与迁移阶段

`apps/reed/` 提供管理页面、GitHub 读取与显式编辑、Skill 来源加载、运行记录、事件和定时调度基础；`apps/swe/` 提供独立检查与架构服务。Skill 已取消编译绑定，旧安装器未恢复。已实现 Codex 接入、授权子集、独立任务工作区、检查与审查门禁、GitHub 任务推进和效果重新采集。测试替身不证明真实账号或实际目标效果；验收证据必须注明这一边界。

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 边界拆分 | 将检查、Schema、范围检查、语言适配器、架构渲染与相应测试迁至 `apps/swe/`；同步 Skill、插件与分发 | 不启动 `reed`，SWE Skills、`swe` 检查及独立架构展示仍可用，已有结果协议与覆盖边界保持有效 |
| 服务基础 | 建设 `reed serve`，提供 GitHub 目标与任务入口、Skill 目录、运行记录和系统设计展示接入 | 页面状态有明确来源，管理动作受授权约束，架构校验与渲染调用 `swe` |
| 调度闭环 | 先以本地数据与模拟 Agent 验证事件、定时、暂停、恢复与停止，再接入一个仓库、Project 与 Agent 验证业务回写 | 场景可重复；重复触发不重复调度，中断后可核对并接续，进展与结果回写原任务 |
| 目标验收 | 在真实 SWE 场景中评价任务交付产生的实际效果 | 能区分任务完成与目标达成，依据效果证据继续、调整、等待或停止 |

架构服务分步迁移：先由 `swe system-design serve` 保持现有独立浏览器与 DSH 使用，`reed` 管理服务就绪后接入统一页面。是否保留独立服务由实际消费者决定，不在拆分时中断现有使用。旧安装器不恢复。

多 Agent 对比、并发调度与通用插件框架等扩展，等真实场景暴露需要再定。

## 待确认问题

1. 首个真实效果验收场景与 Agent；可使用 ReedHarness 自身，也可接入其他业务仓库。这不阻塞调度机制的实现与本地验证。
2. 默认需要人决定的动作，例如合入主分支、推送、发布、外部写入。
3. 首个 Agent 的真实权限隔离与费用预算指标；事件 HTTP 接口、周期配置和运行次数预算已落实。
4. 新 Agent、目标平台与实际业务效果的运行验收；GitHub 回写与任务验收协议见应用设计。
