# 系统设计

> ReedHarness 实现 Harness 的 Business 层：GitHub 管目标与任务，Agent 做判断与执行，Skill 提供完成能力，`reed` 做事件与定时驱动的调度、约束和确定性检查。

本设计取代此前“只聚焦独立任务、不做任务编排、Harness 不调用模型、循环只在 Skill 内”的方案。

## 定位

Harness 由 Environment、Agent、Business 三层组成。ReedHarness 只自建 Business 层：

| 层 | 做法 |
| --- | --- |
| Business | 复用 GitHub 管理目标、任务与证据；自建 Loop 调度、约束与检查，提供领域 Skill |
| Agent | 选用 Codex、Claude Code、pi 等现成 Agent，不自建模型调用与 Agent 循环 |
| Environment | 不自建沙箱，只配置和核对工作区、权限、凭证与预算 |

建设目标：在明确的目标、授权与资源边界内，系统自主形成任务、执行、验证并根据结果继续或调整。人决定目标、重大取舍与授权，并对结果负责。SWE 是首个验证领域。

## 核心概念

| 概念 | 是什么 | 谁判断 |
| --- | --- | --- |
| 目标 | 预期变化、基线、效果证据、授权、预算、停止条件 | 人确定；Agent 在委托内评价进展 |
| 任务 | 本次要解决的问题、输入、交付物、验收条件、授权 | Agent 定义与执行；程序检查与独立审查验收 |
| Skill | 一类工作的知识、方法、工具与检查 | Agent 按任务选用 |
| Loop | 由事件或定时任务触发，根据当前状态决定如何推进目标 | 确定性响应由 `reed` 按规则处理；业务判断交给 Agent，`reed` 检查约束并落实调度 |

委托可以停在任意一层：只用 Skill 和检查命令做局部工作；交给 `reed` 调度 Agent 完成一个任务；或交给 Loop 推进整个目标。

## GitHub 与状态归属

一个业务仓库承载代码、文档、任务与交付，关联的 GitHub Project 管理目标。首版一个 Project 对应一个 Goal，一个仓库 Issue 对应一个 Task。Project 属于用户或组织，再关联到仓库；目标与任务记录不另存一份到 Git。

| 对象 | 权威位置 | 内容与修改责任 |
| --- | --- | --- |
| Goal | Project README | 目标、基线、效果标准、授权、预算与停止条件由人确认；进展与评价单独记录，由 `reed` 根据 Agent 结果回写 |
| Task | Issue | 问题、输入、交付物、验收条件与任务授权由 Agent 提出，`reed` 检查后创建或更新；结果与证据写入评论 |
| 任务进度 | Project 的任务状态字段 | `reed` 根据调度与验收结果更新；完成时同步 Issue 状态，取消不算成功完成 |
| 交付与证据 | PR、commit、检查结果及证据链接 | 关联到对应 Issue；目标评价记录引用实际效果证据 |
| 运行与恢复记录 | `reed` 本地运行目录 | 由 `reed` 保存运行标识、触发处理情况、Agent 会话、工作区、检查点和待回写结果，不另建 Goal/Task 数据库 |

GitHub 是业务状态的唯一事实来源，本地记录只支持调度与恢复。目标定义的变更须由人确认，进展回写不得修改已确认的目标、评价标准、授权与预算。

## 事件与定时驱动的 Loop

Loop 不是从规划到验收依次执行的固定流水线。执行、检查、审查和目标评价都是按当前状态与需要调度的工作。

每轮流程：

1. 接收事件或定时触发，定位相关 Project、Issue 与运行记录。
2. 读取当前状态，核对授权、预算与停止条件。
3. 确定性响应按规则处理；需要业务判断时调度 Agent，决定创建任务、执行、检查、审查、评价目标、等待、请人决定或结束。
4. `reed` 检查决策是否符合约束，落实调度并记录状态，本轮结束，不等待整条工作流程完成。
5. 后续工作结果、状态变化或下一次定时触发再次进入 Loop。

| 触发示例 | 可能的响应 |
| --- | --- |
| 目标启用 | 调度 Agent 分析目标、规划任务 |
| Issue 更新、任务就绪 | 核对当前状态，调度任务执行 |
| Agent 提交交付 | 调度适用检查或独立会话审查 |
| 检查或审查返回 | 推进验收、调度修正、记录受阻或请人决定 |
| 任务完成 | 判断是否推进其他任务或评价目标 |
| 定时触发 | 检查进展、发现停滞、采集目标效果 |
| 人工回复 | 核对决定并恢复等待中的工作 |

事件只是触发依据，不能代替当前状态。重复或同时到达的触发不得导致同一工作重复调度；中断后须能核对状态并接续，不能因结果同步失败而重复已完成的工作。具体调度与恢复机制见[应用设计](app-design.md)。

## 硬规则

以下规则由程序强制，不依赖提示词：

1. 任务授权必须是目标授权的子集。
2. Agent 不能修改目标、评价标准、授权与预算，只能提出变更，由人确认。
3. 任务完成不等于目标达成。目标评价使用目标定义的效果证据，并在评价时重新采集。
4. 调度前检查预算与停止条件；无法满足执行所需的权限约束时不得启动相关工作。权限隔离复用 Agent 与 Environment 提供的能力，范围检查不能代替权限隔离。

## 系统组成与设计入口

检查工具已统一为 `reed`。`reed` 是唯一的程序入口，负责调度、约束和确定性检查，实际工作由 Agent 执行：

- 接收事件与定时触发，根据状态落实调度。
- 读取 GitHub 目标与任务，回写进度、决策与证据。
- 授权、预算与停止条件的检查。
- 调度 Agent，准备任务工作区，并保存运行与恢复记录。
- 交付验收中的程序检查，包括已有的架构、文档与改动范围检查。
- 内嵌 Skill，供执行时使用；插件打包同一份。

旧检查程序入口与 Skill 安装器已移除。

合并后，调度、约束、检查、GitHub 接入与 Agent 接入保持职责清晰。原有检查命令改由 `reed` 提供，仍可独立使用；Loop 按需调用，不把全部检查固定塞入每一轮。

三份设计各自维护唯一的职责范围：本文负责 Harness 的业务协作、硬规则与实施阶段；[应用设计](app-design.md)负责 `reed` 的模块、命令、接入、运行与恢复；[分发设计](distribution-design.md)负责二进制、Skill、插件的构建与交付。程序内嵌和插件打包读取同一份 Skill 源码，具体产物与版本规则由分发设计维护。

## 阶段

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| P0（已实现） | 统一 `reed` 入口，删除旧 Skill 安装器与启动脚本，Skill 编译进 `reed`，同步插件与文档 | 原有检查行为、结果协议、内嵌 Skill 与插件调用链有效；`scripts/verify.sh` 通过，仓库不再保留旧应用入口 |
| P1 | 用一个外部业务仓库、一个 Project、一个 Agent 跑通事件与定时驱动的 Loop，复用 Issue 管理任务 | 场景能重复跑通；事件与定时均能推进工作；重复触发不重复调度，中断后能接续；任务完成后能单独评价目标是否达成 |

P1 中按实际需要确定接入协议、运行记录格式、工作区隔离与接续机制。P1 之后的扩展，如多 Agent 对比与并发调度，等场景暴露需要再定；管理视图先复用 GitHub Project。

## 待确认问题

1. P1 首个场景与首个 Agent。场景应让“任务完成”和“目标达成”可以分开验证，且不用 ReedHarness 自身。
2. 默认需要人决定的动作，例如合入主分支、推送、发布、外部写入。
3. P1 的事件接收方式、定时规则，以及首个 Agent 可落实的权限与预算指标。
